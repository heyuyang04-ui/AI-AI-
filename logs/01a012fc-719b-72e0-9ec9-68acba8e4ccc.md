### 助手（最终答复）

可以研究性移植，但不建议把“完整 openvela”直接运行在 TMS320F28035 上。更准确的结论是：

- 完整 openvela：基本不可行。
- 极度裁剪的 NuttX 内核：理论上能做，但属于新增 CPU 架构移植，不是普通 BSP 适配。
- 量产项目：建议 F28035 保持裸机或 FreeRTOS，openvela 放在另一颗资源更充足的 MCU/MPU 上，两者通过 CAN、SPI 或 UART 通信。

主要障碍有三个：

1. TMS320F28035 只有 60 MHz C28x、128 KB Flash、20 KB RAM。这个容量可以运行电机控制、数字电源和小型 RTOS，但难以容纳 openvela 的 POSIX、文件系统、网络和服务框架。[TI 芯片参数](https://www.ti.com/product/TMS320F28035-Q1)

2. openvela 基于 Apache NuttX，但当前官方支持架构列表中没有 C28x/F28035。列表里的“TMS320-C5471”实际使用 ARM7TDMI，并不是 C28x，因此不能复用其底层移植。[NuttX 支持平台](https://nuttx.apache.org/docs/latest/platforms/index.html)

3. C28x 最棘手的问题是 `CHAR_BIT=16`：`char` 和编译器定义的一个 byte 都是 16 位，而 openvela/NuttX 的大量驱动、协议、文件系统和 POSIX 代码默认一个字节是 8 位。这会影响 `uint8_t`、字符串长度、结构体布局、网络报文、Flash 数据格式等，改造范围远超启动代码和驱动。[TI C28x 字节访问说明](https://software-dl.ti.com/ccs/esd/documents/c2000_byte-accesses-with-the-c28x-cpu.html)

如果坚持单芯片移植，第一阶段只能以“最小 NuttX”为目标：

- 集成 TI C2000 编译器及 EABI。
- 新建 C28x 架构层，实现启动、上下文切换、任务栈、中断和临界区。
- 适配 PIE 中断、CPU Timer、UART、GPIO、看门狗。
- 编写 F28035 链接脚本和 Flash 启动流程。
- 关闭网络、文件系统、图形、多媒体、动态加载及 openvela 服务框架。
- 系统只保留调度器、信号量、消息队列和少数设备驱动。
- 专门审计所有依赖 8 位字节的公共代码。

建议的系统结构是：

```text
主控 MCU/MPU
运行 openvela
  │
  ├── CAN / SPI / UART
  │
TMS320F28035
运行裸机或 FreeRTOS
负责 PWM、ADC、CLA、电机/电源实时控制
```

这种方案既能获得 openvela 的应用和通信能力，也不会破坏 F28035 的硬实时控制性能。

如果你的目标只是让 F28035 获得多任务、队列、信号量和定时器，那么直接使用 TI 官方支持的 FreeRTOS 更合适。若目标确实是研究 C28x 上的 NuttX，我也可以继续帮你建立最小移植骨架；需要提供具体开发板、原理图、现有 CCS 工程、`.cmd` 链接文件以及使用的仿真器型号。

可以，两者都具备足够资源，但如果目标是“尽快把 openvela 跑起来”，优先选择 **Zynq UltraScale+ MPSoC XCZU2EG**。

| 对比项 | XCZU2EG | XC7Z020 |
|---|---|---|
| CPU | 四核 Cortex-A53 + 双核 Cortex-R5F | 双核 Cortex-A9 |
| 位宽 | A53 为 ARM64，R5F 为 ARM32 | ARM32 |
| 实时处理器 | 有独立 R5F | 没有 |
| openvela/NuttX 基础 | 已有 Zynq MPSoC A53 支持 | 当前没有明确的 Zynq-7000 官方板级支持 |
| Linux 共存 | 很适合 | 可以，但隔离能力较弱 |
| FPGA | UltraScale+ PL | 7 系列 Artix-7 级 PL |
| 开发复杂度 | 启动和硬件设计更复杂 | 硬件及启动相对简单 |
| 成本 | 较高 | 较低 |
| 推荐程度 | 首选 | 成本优先的次选 |

XCZU2EG 的核心优势不是单纯“性能更高”，而是现有 NuttX 已经支持 **Zynq UltraScale+ MPSoC 的 ARM64/A53 架构**，官方还有 ZCU111 的启动、串口、网络和 `BOOT.BIN` 生成配置，可以作为 XCZU2EG 的移植基线。[NuttX Zynq MPSoC 支持](https://nuttx.apache.org/docs/latest/platforms/arm64/zynq-mpsoc/boards/zcu111/index.html)

XCZU2EG 还包含四核 Cortex-A53 和双核 Cortex-R5F，非常适合把系统拆成：

```text
Cortex-A53
运行 openvela
负责网络、文件系统、应用、UI、设备管理
        │
        │ RPMsg / OpenAMP / 共享内存 / IPI
        ▼
Cortex-R5F
运行小型 RTOS 或裸机
负责电机、PWM、采样、控制环和硬实时任务
        │
        ▼
FPGA PL
高速接口、编码器、并行采样、硬件加速
```

AMD 官方也把 A53 定位为应用处理单元，把双核 R5F 定位为确定性实时处理单元。[AMD Zynq MPSoC 架构](https://docs.amd.com/r/en-US/ug1449-multimedia/Zynq-UltraScale-MPSoC-Processing-System-Highlights)

需要注意：现有 NuttX 的 Zynq MPSoC 示例主要运行在 A53，不代表 XCZU2EG 可以直接编译烧录。仍然需要适配：

- XCZU2EG 开发板的 DDR、时钟和 MIO 配置。
- FSBL、PMU Firmware、ARM Trusted Firmware 与 openvela/NuttX 的启动链。
- UART、SD、QSPI、Ethernet、USB、CAN 等 PS 外设。
- PL 中自定义 AXI 外设驱动。
- 设备树或固定资源描述。
- Cache、MMU、中断控制器 GIC 和 DMA 一致性。
- A53 与 R5F/PL 的通信。

对于 XC7Z020，它的双核 Cortex-A9、256 KB OCM、外部 DDR 和 FPGA 资源同样足够运行裁剪后的 openvela；芯片本身远比 F28035 合适。[AMD XC7Z020 参数](https://docs.amd.com/api/khub/documents/1L_hkh2pbc5l0Oz7tcLspA/content)

但是它有两个短板：

- 没有独立 R5F，openvela 和实时控制只能共享 Cortex-A9，或把实时逻辑下沉到 FPGA。
- 当前 NuttX 支持列表没有现成的 XC7Z020/Zynq-7000 板级配置，因此可能要补齐 Zynq-7000 的 SoC 支持、GIC、定时器、串口、启动和驱动，工作量反而可能比 XCZU2EG 更大。

最终建议：

- 想做正式产品、Linux/openvela/实时控制共存：选 **XCZU2EG**。
- 想充分利用 A53、R5F 和 FPGA 异构架构：选 **XCZU2EG**。
- 只需要 openvela + 简单 PL、预算敏感，并且已有成熟的 7020 板卡：可以选 **XC7Z020**。
- 如果两块板都还没购买：优先买 **XCZU2EG 开发板**，最好带板厂提供的完整 Vivado/Vitis 工程、FSBL、PMUFW、DDR 配置和原理图。

推荐第一阶段先让 openvela 在 XCZU2EG 的 A53 上启动到 NSH，再依次适配 SD、网络、PL AXI 外设，最后才做 A53/R5F 异构通信。这样成功率最高。

职责划分是合理的：

- F28035继续负责 PFC、LLC 的 PWM、ADC、控制环和本地保护。
- STM32F407负责状态机、参数管理、CAN调度、故障诊断和智能控制。
- ESP32负责 Wi-Fi 和互联网接入。
- openvela运行在 STM32F407 上。
- AI Agent通过工具读取电压、电流、温度、故障码，并执行受限的启停、降额和参数查询操作。

不要让 AI Agent直接参与 PFC/LLC 实时闭环，也不要让网络故障影响 DSP 本地保护。

## 最适合你的新增驱动

建议把现有CAN协议封装成正式的openvela/NuttX设备驱动，而不是应用里直接调用CAN收发：

```text
/dev/pfc0
/dev/llc0
/dev/bms0
```

对上提供统一接口，例如：

```c
ioctl(fd, PFCIOC_GET_STATUS, &status);
ioctl(fd, PFCIOC_SET_ENABLE, &enable);
ioctl(fd, LLCIOC_SET_VOLTAGE, &voltage);
ioctl(fd, BMSIOC_GET_PACK_INFO, &pack);
```

驱动至少包括：

- CAN报文编码和解码
- 节点在线检测
- 心跳与通信超时
- CRC/计数器校验
- 故障码转换
- 电压、电流、功率和温度数据
- 控制命令白名单
- 命令超时与应答确认
- 通信掉线后的安全状态

这个“智能电源设备CAN驱动”是NuttX上游没有的，很符合新增驱动评分项。

## ESP32如何连接更合适

原型验证可以使用UART加ESP-AT，开发最快；正式参赛版本更推荐SPI，吞吐量和稳定性更好。

ESP32可以有两种定位：

- 只提供Wi-Fi链路，TCP/TLS由openvela处理。
- ESP32完成TCP/TLS，F407通过AT或自定义RPC调用。

F407只有192 KB RAM，而AI Agent官方推荐的手表级配置约为256 KB RAM；TLS和网络缓冲还会继续占用内存。[openvela AI Agent内存说明](https://github.com/open-vela/packages_ai_agent)

因此建议：

- 第一版使用CLI-only Agent。
- 关闭飞书、微信、MQTT、MCP、LVGL、语音等非必要模块。
- 让ESP32尽量承担TLS和网络缓冲。
- 使用流式LLM响应。
- 控制上下文长度和JSON缓冲区。
- 将64 KB CCM用于任务栈、控制数据或固定内存池，但注意CCM不能直接用于部分DMA。
- 如果板上有外扩SRAM，可以显著降低风险。

192 KB不代表一定跑不起来，但必须实际测量 `mallinfo`、最大堆占用和各线程栈水位。不要到比赛后期才验证Agent内存。

## 推荐参赛展示场景

作品可以命名为：

> openvela AI智能双级电源与储能管理系统

演示流程：

1. openvela启动并进入NSH。
2. ESP32联网，完成TLS和LLM调用。
3. STM32通过CAN读取PFC、LLC和BMS实时数据。
4. AI Agent回答：“当前系统为什么不能启动？”
5. Agent调用BMS、PFC、LLC状态工具。
6. 识别预充未完成、母线欠压、过温或CAN超时等原因。
7. Agent给出解释和安全操作建议。
8. 用户确认后执行启动或降额命令。
9. 人为制造传感器异常或通信中断。
10. 系统触发DSP本地保护，openvela记录故障，Agent解释故障链路。

这会同时覆盖平台移植、网络、框架、新驱动、AI Tool、多步推理和真实硬件联动。

## 必须做的安全隔离

- DSP必须独立完成过流、过压、欠压、过温、短路和PWM关断。
- STM32或ESP32死机不能阻止DSP保护。
- AI写操作必须使用白名单、范围限制和二次确认。
- Agent不能修改电流环、电压环补偿参数。
- CAN命令应带计数器、超时和状态确认。

可以把核心理由概括为：不是“一个芯片做不了”，而是基于功率控制实时性、系统安全和已有硬件成熟度，主动采用分层异构架构。

现场可以这样回答：

> 理论上可以使用一颗高性能MCU或SoC完成全部功能，但我们的系统包含PFC和LLC两个高速功率闭环，控制周期约为20微秒，对PWM、ADC同步和中断抖动非常敏感。因此我们让DSP专门负责确定性的功率控制和硬件保护；STM32F407运行openvela，负责整机状态机、BMS、CAN通信、参数管理和故障协调；ESP32只负责无线联网。  
>   
> 这种划分把安全关键的控制环与操作系统、网络协议隔离，即使openvela任务或ESP32网络异常，DSP仍能立即关闭PWM并保持功率级安全。代价是芯片和通信接口增加，但我们通过心跳、通信超时、PFC_OK硬件联锁和故障锁存解决。对当前高功率比赛样机而言，可靠性和可验证性比单芯片集成度更重要。

各芯片职责可以明确说成：

| 芯片 | 主要职责 | 选择原因 |
|---|---|---|
| PFC DSP | PFC电流环、电压环、PWM及快速保护 | 20 μs级确定性闭环 |
| LLC DSP | LLC电流环、调制、过流/短路保护 | 独立保护后级功率变换 |
| STM32F407 | openvela、整机状态机、BMS、CAN、参数与诊断 | 适合复杂系统管理和多任务 |
| ESP32 | Wi-Fi/蓝牙、远程监控 | 隔离不确定的网络协议栈 |

如果评委继续追问“为什么PFC和LLC不共用一个DSP”，可以回答：

> PFC和LLC属于两个具有不同采样时刻、PWM时序和保护策略的功率级。分开控制可以减少中断耦合，某一级异常时能够独立快速关断，也方便单独调试和替换。当前两套闭环已经完成硬件验证，强行合并会重新引入时序、标定和保护验证风险。

如果追问“多芯片不是更容易通信失效吗”，回答：

> 是的，这是分布式架构的主要代价，所以我们没有把通信当作默认可靠。系统设置了周期心跳、报文合法性检查、通信超时、故障锁存和硬件PFC_OK联锁；任何关键通信丢失都进入预先定义的安全状态，而不是继续使用旧指令运行。

如果追问“以后量产是否还会这样设计”，回答：

> 当前方案优先保证比赛样机的安全性、可调试性和开发周期。量产阶段可以根据成本和算力评估双核MCU或多核SoC，把STM32和部分DSP功能集成，但必须重新完成实时性、保护覆盖率和故障注入验证，不能简单地为了减少芯片而合并。

最后要避免说“STM32性能不够”。更好的表述是：

> STM32可以承担一部分甚至全部计算，但把高速安全闭环与操作系统和网络任务隔离，是我们经过风险权衡后的工程选择。

# 三、第二阶段：重构串口和Modbus解析

## 3.1 移除当前伪工作线程

当前`QSerialPort`的线程归属不规范：

- `QThread`对象自身仍属于GUI线程；
- 串口指针又在打开后被替换；
- `run()`中的事件循环实际没有带来清晰的线程隔离。

建议第一版直接使用Qt异步串口：

```text
SerialModbusClient
 ├─ QSerialPort
 ├─ QByteArray rxBuffer
 ├─ QTimer pollingTimer
 ├─ QTimer responseTimer
 └─ ModbusStreamParser
```

115200波特率、每500ms一帧，GUI线程完全能够处理，不需要工作线程。

如果后续通信量明显增加，再使用`QObject::moveToThread()`建立真正的串口线程。

## 3.2 新增安全拆包器

新增：

```text
modbuscodec.h/.cpp
modbusstreamparser.h/.cpp
serialmodbusclient.h/.cpp
```

解析逻辑：

1. 在缓冲区中寻找`0x09`；
2. 检查功能码；
3. `0x03`根据字节数字段计算总长度；
4. `0x06`固定8字节；
5. 数据不足则等待下一次`readyRead`；
6. CRC错误丢弃一个字节后重新同步；
7. 正确帧从缓冲区移除；
8. 循环处理缓冲区中的所有完整帧；
9. 缓冲区超过限定长度时清理，防止无限增长。

修正当前问题：

- 同一缓冲区同时存在03和06回复时不能只处理一个；
- CRC失败后不能继续刷新界面；
- 不能只查找`0903/0906`就认为是合法帧；
- 不能读取未验证长度的`dataArray[1]`；
- 不能在GUI线程中调用`QThread::msleep(25)`；
- 重开串口时不能重复连接相同信号槽。

## 3.3 串口事务队列

每次只允许一条未完成Modbus事务：

```text
IDLE
  ↓ 发送查询/控制
WAIT_RESPONSE
  ├─ 正确回复 → IDLE
  ├─ 超时重试 → WAIT_RESPONSE
  └─ 重试耗尽 → COMM_FAULT
```

建议：

- 查询周期：500ms；
- 回复超时：300～500ms；
- 最大重试：2次；
- 连续3～5次失败：标记STM32离线；
- 不再每次超时弹模态窗口，改为状态栏和日志提示。

# 七、第六阶段：重新设计STM32控制寄存器

当前STM32的功能码06直接根据地址修改`g_SysStatus`内存，不适合作为Agent控制接口。

建议分离：

```text
0x0000～0x0015：只读遥测区
0x0100～0x010F：控制命令区
0x0200～0x020F：命令结果和拒绝原因
```

## 7.1 推荐控制帧

增加Modbus功能码`0x10`，一次性写完整命令：

| 地址 | 字段 |
|---:|---|
| 0x0100 | 命令序号 |
| 0x0101 | 动作：HOLD/DERATE/STOP/START |
| 0x0102 | 目标电压×10 |
| 0x0103 | 目标电流×10 |
| 0x0104 | ARM令牌/会话号 |
| 0x0105 | 保留/协议版本 |

STM32先复制到临时结构，全部验证通过后再原子提交。

不能出现：

```text
先启动输出
→ 再检查电压
→ 再检查电流
```

## 7.2 命令权限

- STOP：始终可接受；
- DERATE：只能降低目标；
- SET_TARGET：必须在范围内；
- START：必须经过ARM；
- CLEAR_FAULT：单独定义，Agent不能调用；
- 硬件故障：必须本地人工清除；
- 通信失联：进入预定义安全状态。

## 7.3 启动两步确认

```text
人工点击ARM
    ↓
STM32返回ARM成功和临时令牌
    ↓ 3秒以内
人工点击执行
    ↓
STM32重新检查BMS、DSP、温度、电压
    ↓
允许后启动
```

Agent只能提出`request_start`，不能完成第二步确认。
